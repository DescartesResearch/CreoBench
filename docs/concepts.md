# Concepts

CreoBench lets you simulate realistic user traffic against your services
so you can see how they behave under different traffic patterns. The
traffic generated by CreoBench consists of individual requests, which this
documentation refers to as **transactions**.

This page walks you through the building blocks of a load test so you can
understand the rest of the documentation.

## The Big Picture

A load test consists of two components working together:

- One or more **load generator instances** send transactions to your
  services. Each load generator instance records information about the
  transactions it sends, such as how long it took to receive a response
  and whether the transaction was successful.
- The **orchestrator** coordinates the load test. You start it with your
  load test configuration, and it connects to the load generator instances,
  tells them what to do, collects their results, and produces the final
  output.

For smaller load tests, you can run the orchestrator and the load
generators on a single machine. For larger tests, you can distribute load
generator instances across multiple machines. The orchestrator coordinates
all of them as part of the same load test.

## Defining the Load

Before running a load test, you describe the traffic pattern you want
CreoBench to generate. A load definition consists of several parts:

### Load Profile

A load profile defines how many transactions to send during each period of
the test. Each step in a load profile contains:

- A **deadline**, expressed relative to the start of the load test.
- The target number of transactions to send before that deadline.

The time between two consecutive deadlines is called the **load interval**.
Although load intervals are often one second long, they can have any
duration.

For example, a profile with the steps `(1s, 10)`, `(3s, 100)`, and
`(5s, 10)` specifies the following targets:

- Send 10 transactions during the first one-second load interval.
- Send 100 transactions during the next two-second load interval.
- Send 10 transactions during the final two-second load interval.

You can use load profiles to create gradual ramps, sudden spikes, or a
steady rate of traffic. See [Load profiles](load-profiles.md) for details.

### Virtual Users

Each concurrent session maintained by your load test is called a **virtual user**
(VU). A VU is similar to a browser tab: it retains state between
transactions, including cookies, headers, and tokens. This allows it to
behave more like a real user interacting with your application.

The VU count specifies how many virtual users each load generator instance
maintains concurrently. When a test uses multiple load generator instances,
each instance maintains the configured number of virtual users. Increasing
the VU count allows the test to maintain more concurrent activity, but also
requires more resources on each load generator instance. See
[Scripting](scripting.md) for more information about sizing the VU
pool.

### Scripts

A Lua script defines what each virtual user actually does. It typically has
two parts:

- A **setup** function that defines the transactions sent once for each VU
  before the load test begins. For example, these transactions might
  authenticate the VU and store a session token.
- A **requests** function that defines the sequence of transactions each VU
  performs repeatedly during the load test.

Scripts can read from and write to a per-VU key-value store. This allows
state from one transaction, such as a session token or another response
value, to be used by a subsequent transaction. See
[Scripting](scripting.md) for more information.

### Service Registry

A service registry maps logical service names to base URLs. Lua scripts
refer to services by name, such as `auth` or `api`, and the registry
resolves those names to their actual endpoints.

This lets you run the same script against different environments, such as
local testing and public cloud VMs, by changing the registry file instead
of modifying the script. See [Service registry](service-registry.md) for
details.

### Warmup

A warmup phase runs a short period of traffic before the main test begins.
Its purpose is to prepare the system for the test by priming caches,
establishing connection pools, and warming up JIT compilers. This helps
ensure that the main test results reflect steady-state performance rather
than cold-start effects. See [Warmup](warmup.md) for configuration details.

## Load Test Flow

At startup, the orchestrator distributes the test configuration -- such as the
load profile, script, service registry, and warmup settings -- to the load
generator instances. It also divides the load profile equally among the
instances so that they can generate the required total load together.

Each load generator instance then creates its virtual users and executes the
setup transactions defined by the script. After completing setup, the
instance reports its status back to the orchestrator. The orchestrator waits
until every instance has finished setup before issuing the start command.

The start command causes all load generator instances to begin their warmup
and load phases together. During the load test, the orchestrator
continuously checks that the instances remain synchronized. If an instance
falls out of sync, the orchestrator aborts the load test.

During each load interval, a load generator instance uses its assigned
portion of the load profile to determine how many transactions to send
before the interval's deadline. It spreads those transactions across the
interval to maintain the target rate. Transactions are grouped into
**batches**, which are small groups of transactions scheduled to start
at approximately the same time. Between batches, the load generator waits
briefly before scheduling the next group.

Each transaction in a batch is assigned to an available virtual user. The
virtual user runs the next step in its script, sends the corresponding HTTP
request, and passes the response back to the script. CreoBench records the
outcome of every transaction, including transactions that fail, time out,
or cannot be sent—for example, because the load generator is too busy to
schedule them in time.

## Reporting

Each transaction produces a result, such as success, failure, timeout, or
dropped. Load generator instances stream transaction results to the
orchestrator throughout the load test. At the end of each load interval,
they send the results for that interval to the orchestrator.

The orchestrator combines the results from all load generator instances and
makes them available in several formats:

- **Console** — Displays a live progress line that shows the test's status
  as it runs.
- **Interval CSV** — Provides one row per load interval, including counts
  for each outcome type and the average response time.
- **Transaction CSV** — Provides one row for each transaction, including
  detailed timing and outcome information.

Since load intervals can have different durations, the interval CSV follows
the deadlines defined by the load profile rather than using a fixed-duration
interval.

### Response Time vs. Service Time

For each transaction, CreoBench records both **response time** and
**service time**. These metrics describe different parts of the transaction's
lifecycle.

**Response time** is the end-to-end duration from when the transaction
starts until its outcome is known. This includes time spent waiting for an
available virtual user, time spent waiting for the transaction to be sent,
and the time taken to receive a response or determine that the transaction
failed, timed out, or was dropped.

**Service time** is the time spent communicating with the service. It starts
when the HTTP request is sent and ends when a response is received or the
request reaches a terminal outcome, such as a failure or timeout. A dropped
transaction has no service time because its HTTP request was never sent.

The difference between response time and service time shows how much time
was spent before the request reached the service. A large difference can
indicate that the load generator does not have enough available virtual
users or resources to schedule transactions on time.

See [Outputs](outputs.md) for a detailed description of the available
results.

## Putting It All Together

A typical load test follows these steps:

1. **Configure** — You launch the orchestrator with a load profile, a Lua
   script, a service registry, and warmup settings.
2. **Connect** — The orchestrator connects to the load generator instances,
   distributes the configuration, and divides the load profile evenly among
   them.
3. **Setup** — Each load generator instance creates its virtual users and
   executes the script's setup transactions. The instances report back to
   the orchestrator when setup is complete.
4. **Start** — After every instance has finished setup, the orchestrator
   sends a start command to all instances. They then begin the warmup and
   load phases together.
5. **Run** — During the warmup and main load phases, virtual users execute
   the script and generate transactions according to the load profile. The
   load generator instances record each transaction's outcome and timing,
   and stream the results to the orchestrator throughout the test. The
   orchestrator continuously checks that the instances remain synchronized
   and aborts the test if they fall out of sync.
6. **Report** — At the end of each load interval, the load generator
   instances send the results for that interval to the orchestrator. The
   orchestrator aggregates and persists the results from all instances.

For the full command-line reference, see [CLI reference](cli-reference.md).
If something goes wrong, see [Troubleshooting](troubleshooting.md).
